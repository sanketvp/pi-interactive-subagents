PACKAGE PINNING & BUILTIN COMPARISON
Builtin behavior (PROVEN from docs):
- `pi install npm:pkg@1.2.3` pins npm versions; `pi update --extensions` skips pinned specs
- `pi install git:host/user/repo@v1.0.0` pins git refs; `pi update --extensions` reconciles refs
  (reset/clean/npm install if ref moves, but does not advance tags)
- Project .pi/settings.json carries team-shareable package list; auto-loads on Pi startup
- No builtin backup/restore of settings.json or package state
- No builtin multidevice sync of configuration
- No custom backup code is necessary if pinning pins your exact constraint (version + git ref)
- Team sharing works out-of-box via .pi/settings.json in VCS

Conclusion: Builtin pinning is sufficient for single-machine reproducibility. Custom backup code
becomes valuable only for: (a) multidevice sync (pi-sync reuses), (b) granular rollback
(git-based or snapshot), (c) security audit trails (pi-sync's immutable snapshots provide this).

RECOMMENDATION SUMMARY

REUSE FROM CATALOG (PROVEN):
1. @narumitw/pi-sync v*.*.* — backup/restore and multidevice config sync (if external
   storage acceptable; replaces most custom code)
2. @narumitw/pi-stamp — session identity metadata (timestamps, model provenance, tokens)
3. @narumitw/pi-statusline or pi-powerline-footer — footer customization (choose style)

DO NOT BUILD CUSTOM CODE FOR:
- Config backup/restore → use pi-sync + local S3/R2 or GitHub private repo
- Package pinning → use builtin `pi install npm:@scope/pkg@X.Y.Z` and git refs
- Session UUID tracking in footer → pi-stamp covers this; extend as needed
- Team config sharing → use project .pi/settings.json in VCS + pi-sync for binary sessions

UNMET REQUIREMENTS:
1. Explicit session UUID in footer (full UUID, not truncated) — pi-stamp shows response IDs
   behind opt-in expansion; may need custom pi-stamp patch or new extension
2. Local-only backup (no external storage) — pi-sync requires remote; no builtin local archive
3. Upgrade safety audit — neither builtin nor catalog provides pre-upgrade/post-upgrade diff;
   custom snapshot at ~/ root before `pi update` is safest

BLOCKERS: None. All recommended extensions are production npm packages with live READMEs,
GitHub sources, and active authors.

LESSON
Pi's builtin extension+settings architecture is mature enough that most "custom Pi harness
code" needs (backup, config sync, package management) are better served by reusing published
extensions. The three recommended packages (@narumitw/pi-sync, pi-stamp, pi-statusline/
pi-powerline-footer) are upgrade-safe, actively maintained, and transparent (MIT). No need to
reinvent config management; extend catalog offerings instead.
