SYNTHESIS

Best Tmux Worker Orchestrator: @maplezzk/pi-interactive-subagents (3.7.1)
Best Model Routing Layer: pi-provider-litellm (2.3.0)

Combined Architecture:
┌─ Coordinator (Pi session, Orca tab 1)
│  └─ subagent({name, agent, task, model}) via maplezzk extension
│     ↓ queries litellm alias providers for model-family dispatch
│     ↓ resolves model via pi-provider-litellm
│  ├─ Worker 1 (tmux pane 2): runs Pi agent on resolved model
│  ├─ Worker 2 (tmux pane 3): runs Pi agent on resolved model
│  └─ Results steer back into main session

GAPS AGAINST AGENTS.MD REQUIREMENTS

Orchestration Contract Guarantees Not in Any Extension:
1. Exact session UUIDs tracked across parent/child launches — no extension enforces Pi session ID provisioning to workers
2. Parent reload/recovery protocol — no extension documents checkpoint/resume on parent crash
3. Owned cleanup (who kills which pane, in what order) — subagent extension manages pane lifecycle but no explicit ownership model
4. Safe takeover/steering during mid-execution — litellm + maplezzk provide mid-turn result steering, but not mid-pane takeover
5. Focus-change blocker (Orca 1.4.197) — maplezzk does not document Orca compatibility or focus-change workaround

KEY LESSON LEARNED

Pi's extension ecosystem provides excellent building blocks (subagent spawning, model providers, fleet widgets), but does not enforce orchestration contract clauses from AGENTS.md (session UUIDs, cleanup ownership, parent reload recovery, no focus changes). These are architectural requirements that require custom coordinator glue above extensions.

UNMET FUNDAMENTAL REQUIREMENT

No extension provides documented proof of: "visible interactive workers tiled in ONE Orca tab via tmux without focus changes; exact session UUIDs; safe steering/takeover; parent reload/recovery; owned cleanup; upgrades must not erase customizations."

This is the AGENTS.md orchestration contract. Extensions handle worker spawning and model routing, but the contract is coordinator-level, not extension-level.
